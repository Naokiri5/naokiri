## Source findings to verify

1. **High, concurrent approval or cancellation.** Baseline `exec/oms.ts:submitEntry` loads an existing pending approval before the write transaction, then updates that order by ID inside the transaction. The unique key protects inserts of new orders but does not guard an already-existing approval row. `decideApproval` and `expireApprovals` also read before updating. Verify with separate processes racing an approval and cancellation or with two approvers, then assert exactly one valid terminal transition and one set of accounting writes.
2. **High candidate, executable price versus risk sizing.** Entry risk uses decision `entryRef` to check deviation and the current top ask to size before fetching `simulateEntryFill`'s depth-walk price. Post-simulation checks cover cash, slippage, stop and target placement. Verify whether policy exposure and planned risk caps remain valid across adverse quote movement, then measure risk from recorded fills.
3. **Medium candidate, post-commit publication.** Core accounting commits before journal and notification side effects. Recovery evidence should show which effects are reconstructed after crashpoints immediately after commit. The baseline entry path has no visible durable publication queue.
4. **Documentation drift.** `docs/KNOWN_LIMITATIONS.md` describes a November 16 snapshot. Main now contains connected chart replay, deployment readiness and configurable scheduled backups. Older `docs/REQUIREMENTS_TRACEABILITY.md` similarly lists market breadth as missing, although `marketBreadth()` is supplied by `buildContext`. Revalidate these statements against fresh runtime results before assigning operational status.

No code consolidation or certification is claimed by this architecture trace.
